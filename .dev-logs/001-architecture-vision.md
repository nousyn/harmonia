# Harmonia 架构重构愿景

> 创建时间: 2026-03-22
> 状态: 讨论中

## 一、为什么要重构

### 1.1 当前架构（MCP Server）的根本矛盾

Harmonia 当前以 MCP Server 形态运行，依赖 coordinator（LLM agent）调用 MCP 工具来推进工作流。这个架构存在不可调和的矛盾：

- **MCP 本质是"工具箱"（被动、弱控制）**：agent 想用就用、不想用就不用
- **Harmonia 的初衷是强管控**：节点顺序、gate 阻塞、schema 校验、审批——这些在 MCP 架构下全部是软约束
- **coordinator 是 LLM agent，行为不可控**：跳过 `sessions_spawn` 编造 session ID、不调用 `artifact_write` 就声称有限制、忽略 Next Action 指引
- **子 agent 环境不可控**：子 agent 是否配置了 Harmonia MCP、是否会调用 `artifact_write`、prompt 是否完整传递，Harmonia 完全无法保证

### 1.2 核心结论

> 如果 Harmonia 的强管控初衷达不到，剩下的实现没有意义。
> MCP 架构在根本上无法实现强控制，必须转变为独立编排应用。

## 二、目标架构

### 2.1 总体分层

```
┌─────────────────────────────────────────────┐
│          Harmonia 工作流引擎（强控制层）       │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  │
│  │ 节点管理  │  │ Gate 阻塞 │  │ Artifact │  │
│  │ 状态机    │  │ 条件评估  │  │ 读写/审批 │  │
│  └──────────┘  └──────────┘  └──────────┘  │
├─────────────────────────────────────────────┤
│          Agent 调度层（拉起/监控/回收）        │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  │
│  │ 任务分派  │  │ 生命周期  │  │ 结果收集  │  │
│  │          │  │ 管理      │  │          │  │
│  └──────────┘  └──────────┘  └──────────┘  │
├─────────────────────────────────────────────┤
│          Agent 通信层（预留/渐进实现）         │
│  ├── 1:1 消息传递（Harmonia 转发）           │
│  ├── 组内广播                                │
│  └── 结果整合                                │
├─────────────────────────────────────────────┤
│          Agent 适配层                        │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  │
│  │ OpenCode │  │ OpenClaw │  │ 其他      │  │
│  │ 适配器   │  │ 适配器   │  │ Agent     │  │
│  └──────────┘  └──────────┘  └──────────┘  │
└─────────────────────────────────────────────┘
```

### 2.2 各层职责

#### 第一层：工作流引擎（强控制层）

这是 Harmonia 的核心，已有实现的基础。负责：

- **节点状态机**：`pending → active → completed/failed`，单向不可逆
- **Gate 阻塞**：artifact_approved 等条件的硬阻塞
- **Artifact 管理**：读写、schema 校验、review 审批
- **工作流定义解析**：workflow.json、角色文件、schema 文件

这一层的关键变化：**不再被动等待 agent 调用工具，而是主动驱动流程推进**。

#### 第二层：Agent 调度层

这是重构的核心新增层，Harmonia 从"被调用"变为"主动调度"：

- **任务分派**：根据当前活跃节点，决定启动哪个 agent、传递什么上下文
- **生命周期管理**：启动 agent、监控执行、超时处理、异常回收
- **结果收集**：agent 完成后，收取产出物（artifact 内容、执行报告），写入 Harmonia 的 artifact 系统

Harmonia 在此层实现"指挥官"角色——agent 是专业兵种（opencode 写代码、openclaw 做用户沟通），Harmonia 负责调度它们。

#### 第三层：Agent 通信层

为 agent 间协作提供通信基础设施。**优先级最低，可渐进实现**：

- **1:1 消息传递**：Harmonia 作为中枢转发 agent 间消息
- **组内广播**：将一个 agent 的产出广播给同组其他 agent
- **结果整合**：多个 agent 的产出合并为统一结果

通信层由 Harmonia 完全控制：

- **谁能和谁通信** → 工作流定义决定
- **什么时候通信** → 节点流转决定
- **传递什么内容** → Harmonia 过滤/整合后注入

这与 OpenClaw 的 Gateway 模式类似（所有通信经过中枢），但 Harmonia 是**主动编排者**而非被动路由器。

#### 第四层：Agent 适配层

统一的 agent 接口抽象，屏蔽不同 agent runtime 的差异：

- **OpenCode 适配器**：对接 OpenCode（写代码、调试、执行开发命令）
- **OpenClaw 适配器**：对接 OpenClaw（用户沟通、多渠道消息）
- **通用适配器**：支持未来对接其他 agent（Claude Code、Codex 等）

每个适配器需要实现的核心接口：

- 启动 agent session
- 发送任务/消息
- 接收结果/产出
- 查询状态
- 终止 session

## 三、愿景场景：Dev 工作流

### 3.1 理想形态（远期）

```
Harmonia Dev 工作流
  │
  ├── 产品组
  │     ├── coordinator（PM）
  │     └── 需求分析师
  │     └── 组内协作 → 输出：需求文档
  │
  ├── 架构组
  │     ├── 架构师 A（系统设计）
  │     └── 架构师 B（技术选型）
  │     └── 组内协作 → 输出：架构设计文档
  │
  ├── 开发组
  │     ├── 前端开发
  │     └── 后端开发
  │     └── 组内协作 → 输出：代码实现
  │
  └── 测试组
        ├── 单元测试
        └── 集成测试
        └── 组内协作 → 输出：测试报告
```

### 3.2 现实约束

这个愿景**强依赖 LLM 的稳定性**——组内分工、多 agent 协作讨论、结果整合，都需要 LLM 能可靠地理解上下文、遵循指令、产出一致的结果。

**这不是 Harmonia 的瓶颈，而是 LLM 的瓶颈。** Harmonia 的架构应该：

- 在强控制层面做到极致
- 在通信层面预留扩展能力
- 不因 LLM 的不稳定性而降低架构目标

## 四、与 OpenClaw 的关系定位

**Harmonia 独立，对接 OpenClaw 作为 agent runtime 之一。**

- Harmonia 是更高层的编排者
- OpenClaw 是被调度的执行者之一（主要用于用户沟通场景）
- OpenCode 是另一个被调度的执行者（主要用于编码场景）
- 通过适配层统一接口，Harmonia 不绑定任何特定 agent

### 4.1 可借鉴 OpenClaw 的能力

| OpenClaw 能力      | Harmonia 如何借鉴                                                         |
| ------------------ | ------------------------------------------------------------------------- |
| Gateway 中心化通信 | Harmonia 做通信中枢，所有 agent 通信经过 Harmonia                         |
| ACP 协议           | 复用 ACP 对接外部 agent（Codex、Claude Code 等）                          |
| Announce 系统      | agent 完成后主动通知 Harmonia（但 Harmonia 要求强制通知，非 best-effort） |
| 安全围栏           | agent 产出标记为不可信，Harmonia 校验后才接受                             |
| Session 隔离       | 每个 agent 独立 session，Harmonia 控制上下文注入                          |

### 4.2 OpenClaw A2A 的局限

OpenClaw 的 A2A 乒乓对话是目前最接近"agent 间讨论"的实现，但：

- **只支持 1:1**，不支持多方讨论
- **最多 5 轮**，不够灵活
- **agent 主动发起**，不是编排者控制
- **异步、best-effort**，不保证结果

Harmonia 的通信层需要在此基础上增强，但这是**后期优化**，不是当前重构重点。

## 五、待确定的问题

以下问题需要在后续讨论中逐一确定：

1. **Harmonia 作为独立应用的运行形态**：CLI？常驻进程？Web 服务？
2. **Agent 适配层的具体协议**：复用 ACP？自建？如何处理不同 agent 的能力差异？
3. **工作流引擎的主动驱动机制**：事件驱动？轮询？状态变更触发？
4. **artifact 如何在 agent 和 Harmonia 之间传递**：文件系统？API？内存？
5. **用户交互界面**：如何进行 review/approve？CLI？Web UI？
6. **与现有 MCP 实现的迁移策略**：渐进迁移还是重写？
