## 运行形态与基础设施

### Q1. Harmonia 的运行形态

**来源**: 001 §五、002 §七、004 §八

**问题**: Harmonia 作为独立编排应用，应该是 CLI 工具、常驻进程还是 HTTP 服务？

**状态**: ✅ 已确认

**结论**:

Harmonia 是 HTTP 服务，前后端分离架构。

- **Core 不依赖 HTTP**，HTTP 层是薄壳（接入层），Core 去掉 HTTP 照样能跑
- 架构分层：
  ```
  HTTP 层（薄壳）
    ├── /a2a/*   → A2A 协议端点
    ├── /api/*   → Web UI API
    └── /ws      → WebSocket（状态推送）
  Harmonia Core（纯逻辑）
    ├── 工作流引擎
    ├── Agent 调度
    └── Artifact 管理
  ```
- 实施节奏：先 Core + HTTP API，后加 Web UI
- 与 OpenClaw Gateway 的区别：Gateway 是厚 runtime 引擎（105+ 方法），Harmonia HTTP 层是薄接入壳（预计 10-20 个端点），核心逻辑在 Core 中

### Q2. 工作流引擎的主动驱动机制

**来源**: 001 §五、002 §七、003 §七

**问题**: event loop 如何设计？事件驱动？轮询？状态变更触发？

**状态**: ✅ 已确认

**结论**:

事件驱动为主，辅以超时检测机制。

- **事件循环是主驱动**：业务事件（`node.completed`、`gate.passed`、`artifact.approved` 等）驱动工作流推进
- **每个派发任务注册超时定时器**：任务派发时设定 deadline，到期触发超时检测
- **超时触发时通过适配器检查 agent 实际状态**，再决定下一步：
  - agent 还活着、正常运行中 → 续期（延长 deadline）
  - agent 还活着、但卡住/无进展 → `task.stalled` 事件，进入错误处理
  - agent 进程已退出/连接断开 → `task.failed` 事件，进入错误处理
  - agent 不可达 → `agent.unreachable` 事件，重试或错误处理
- **不单独设监控器**：定时器是触发源，适配器健康检查是判定手段，合并为一个机制，避免重复工作和竞态
- 超时事件和业务事件汇入同一个事件循环处理

## Agent 适配器层

### Q3. 能力声明的粒度

**来源**: 003 §七

**问题**: 当前定义了 `dispatchTask`、`pushMessage`、`userInteraction` 三种。是否需要更细粒度（如 `sandbox`、`budgetControl`、`sessionResume`）？还是保持粗粒度，细节放在 `constraints` 里？

**状态**: ✅ 已确认（部分，与 Q6 关联）

**结论**:

保持粗粒度。

- **去掉 `userInteraction`**——Harmonia 引擎不需要这个信息做任何决策。agent 怎么跟用户交互是 agent 自己的事，Harmonia 只管 `pushMessage` 推消息出去、等 agent 通过 API 回传结果
- **只保留 `dispatchTask` 和 `pushMessage` 两种能力**
- **sandbox、budgetControl 等细节放在 `TaskPayload.constraints` 中**，适配器不支持的 constraint 直接忽略
- **capabilities 声明本身是否需要存在**取决于 Q6（workflow 节点是显式指定 agent 还是按能力匹配）——如果显式指定 agent，则 capabilities 声明不需要，适配器的可选方法本身就是能力表达

### Q4. 适配器对接方式：CLI 还是 SDK/API 起步？

**来源**: 003 §五、§七

**问题**: 短期 CLI 子进程模式已推荐，但 Harmonia 若确认为 HTTP 服务，是否应直接从 SDK/API 起步？

**状态**: ✅ 已确认

**结论**:

CLI 子进程起步。

- **CLI 与 Harmonia 作为 HTTP 服务不矛盾**——调 agent 的方式是内部实现细节，HTTP 服务内部 spawn 子进程完全正常
- **CLI 最简单可控**：不需要 agent 预先启动为服务，生命周期由 Harmonia 完全控制（spawn → wait → collect），四个 agent 的 CLI 模式高度一致
- **SDK/API 当前没有强需求**——Harmonia 只需要"派任务 → 等结果"，CLI 够用
- **适配器接口不变**（`dispatchTask` / `pushMessage`），后续按需将内部实现从 spawn CLI 换成调 SDK，对引擎层透明

### Q5. TaskPayload 的 context 设计

**来源**: 003 §七

**问题**: 传递完整 artifact 内容给 agent，还是只传引用（让 agent 自己读取）？

**状态**: ✅ 已确认

**结论**:

默认传完整内容，大文件传 artifact 产出路径。

- **默认传完整内容**：适合 CLI stdin 注入上下文，大部分 artifact 是文档，体量可控
- **大文件直接传 artifact 产出路径**：不创建临时文件，artifact 本身就有持久化存储路径
- **适配器层根据内容大小决定用哪种方式传递**，对引擎和 agent 透明
- **当前假设同机部署**，文件路径直接可达。未来分布式场景再加 API 获取的备选通道

### Q6. 多 agent 同能力时的选择策略

**来源**: 003 §七

**问题**: 如果 OpenCode、OpenClaw、Claude Code 都声明了 `dispatchTask`，workflow 节点如何指定用哪个？显式指定 `agent: "opencode"`？还是引擎做负载均衡？

**状态**: ✅ 已确认

**结论**:

workflow 显式指定 agent，配置在角色（Role）上。

- **不做能力匹配/负载均衡**——工作流设计者一定有明确意图，引擎不需要自动选择
- **agent 配置在角色定义中**，而非节点上：
  ```json
  {
    "roles": {
      "pm": { "agent": "openclaw", "systemPrompt": "..." },
      "developer": { "agent": "opencode", "systemPrompt": "..." }
    },
    "nodes": [
      { "id": "write-prd", "roles": ["pm"] },
      { "id": "write-code", "roles": ["developer"] }
    ]
  }
  ```
- **理由**：语义自然（agent 选型跟着角色走）、集中管理（改一处全生效）、避免不一致（不用每个节点重复配置）
- **不支持节点级 override**——当前不需要这个复杂度
- **capabilities 声明不需要**——显式指定 agent 后，引擎直接按 type 查适配器注册表，不需要能力匹配逻辑

**对 Q3 的补充影响**：capabilities 声明确认不需要。适配器的可选方法（`pushMessage?`）本身就是能力表达，引擎直接检查方法是否存在即可。

### Q7. 适配器注册机制

**来源**: 003 §七

**问题**: 适配器是硬编码在 core 里，还是像 workflow 一样插拔式加载？

**状态**: ✅ 已确认

**结论**:

当前硬编码，代码结构上预留插拔空间。

- **当前阶段硬编码**：只有 4 个 agent，插拔式的动态加载、运行时校验、配置管理、版本兼容、错误隔离等复杂度收益比太低
- **代码结构预留插拔可能性**：适配器放独立目录、实现统一接口、通过注册表模式管理，未来需要插拔时改造成本低

---

### Q8. 错误处理和重试策略

**来源**: 003 §七

**问题**: agent 执行失败后如何处理？是否支持自动切换到另一个同能力的 agent？

**状态**: ✅ 已确认

**结论**:

当前阶段只做"标记节点失败 + 通知 coordinator"，不做自动重试和 agent 切换。

- **失败来源**：agent 返回失败结果、超时确认失败、进程崩溃、agent 不可达
- **默认行为**：标记节点为 failed，通知 coordinator（如有），由人工介入决策
- **不做自动重试**：判断"何时该重试"的逻辑复杂且易出错，当前阶段没有足够的失败数据支撑策略设计
- **不做 agent 切换**：Q6 已确认角色显式绑定 agent，没有"同能力备选 agent"的概念
- **未来演进**：积累实际失败数据后，再针对性加重试策略

## 对外接口（A2A）

### Q9. A2A 协议绑定选择

**来源**: 004 §九

**问题**: JSON-RPC vs gRPC vs REST？（003 推荐 JSON-RPC）

**状态**: ✅ 已确认

**结论**:

JSON-RPC 2.0 over HTTP(S)。

- **A2A 官方主推方向**，SDK 生态（Python/JS/Go/Java/.NET）都围绕 JSON-RPC 实现
- **Harmonia 不是高吞吐场景**，gRPC 性能优势用不上
- **JSON-RPC 比 REST 更契合 A2A 的操作语义**（`SendMessage`、`GetTask` 是 RPC 调用，不是资源 CRUD）
- 注：A2A 是最后加的薄壳，当前阶段不实现

## 数据与交互

### Q13. Artifact 在 agent 和 Harmonia 之间的传递方式

**来源**: 001 §五

**问题**: 文件系统？API？内存？

**状态**: ✅ 已确认

**结论**:

Agent 写入 Harmonia 指定位置，Harmonia 根据配置决定是否校验。

- **写入方式**：Harmonia 通过 prompt 注入告知 agent 产出写入位置，复用现有 `ArtifactDefinition.output` 模板机制（`{global}` / `{project}` 等）
- **校验类型**三种：
  - `schema`：JSON Schema 校验，适用于结构化文档（PRD、需求 JSON 等）
  - `command`：执行自定义校验命令，适用于有明确检查手段的产出
  - `none`：不校验，适用于代码类产出、无法定义校验标准的产出
- **默认不校验**（`none`），需要校验的在 `ArtifactDefinition` 中显式声明
- **不校验的产出通过后续流程节点保证质量**（测试节点、人工审批等），Harmonia 的强管控在流程层（节点顺序、Gate 阻塞、状态机不可逆），不在内容层
- **当前文件设计基本能支撑**：数据目录结构、artifact 路径解析、schema 校验等现有能力可复用。主要调整是写入流程方向：从"agent 调 MCP 工具写入"变为"agent 直接写文件 → Harmonia 主动检查"
- **`unmanaged` 概念在重构后不再需要**——所有 artifact 都是 agent 直接写文件，区别只在于配没配校验规则

### Q14. 用户交互界面

**来源**: 001 §五

**问题**: review/approve 通过什么进行？CLI？Web UI？还是完全委托给 Coordinator？

**状态**: ✅ 已确认

**结论**:

审批完全委托给 Coordinator，Web UI 整体推迟（远期，与 A2A 同优先级）。

- **审批主路径是 Coordinator**：用户通过飞书/Slack 等渠道和 coordinator 对话，coordinator 调 Harmonia HTTP API 完成审批
- **没有 Web UI，Harmonia 所有核心功能都能正常运行**：
  - 工作流执行全流程：Core + 适配器 + Coordinator 覆盖
  - 审批：Coordinator 处理
  - 查看状态/Artifact：HTTP API 返回 JSON
  - 管理操作（注册项目、配置工作流）：CLI 命令或 HTTP API
  - 错误排查：终端日志或 HTTP API
- **Web UI 是远期增强**，提供更友好的监控和管理体验（全局概览、历史记录可视化等），但不是功能上的必需品
- **Web UI 的功能范围推迟到远期讨论**，包括是否支持审批操作
- **后端不受影响**：所有操作都走 HTTP API，未来加 Web UI 只是多一个前端消费者

**实施优先级**:

1. Core（工作流引擎 + 事件驱动）
2. 适配器层
3. HTTP API
4. Coordinator 对接验证
5. A2A（远期）
6. Web UI（远期）

## 迁移

### Q15. 现有代码的迁移策略

**来源**: 001 §五、002 §七、003 §七

**问题**: 渐进迁移还是重写？哪些模块保留、哪些重写？

**状态**: ✅ 已确认

**结论**:

在现有代码仓库上改造，不重写。

- **底层模块直接复用**（现有实现没有问题，重写不会带来改进，只增加成本和风险）：
  - `registry.ts`：数据目录管理、路径函数、注册表 CRUD
  - `state.ts`：工作流状态持久化
  - `reviews.ts`：审核状态管理
  - `steps.ts`：分步状态管理
  - `schema.ts`：JSON Schema 校验
- **中间层模块在现有基础上扩展**：
  - `workflow-engine.ts`：复用状态转换函数，新增事件驱动的主动推进逻辑
  - `artifacts.ts`：复用路径解析和读取，调整写入流程方向
  - `plugin.ts`：复用加载逻辑，扩展 role 定义（加 agent 字段）
  - `types.ts`：保留核心类型，新增事件、适配器、TaskPayload/TaskResult 等类型
- **上层模块替换/新写**：
  - `index.ts`：MCP Server 入口 → HTTP 服务入口
  - `tools/*.ts`：MCP 工具 → HTTP API endpoints
  - `dispatch.ts`：被动记录 → 主动管理 agent 生命周期（重写）
  - `cli/*.ts`、`setup/*.ts`：MCP 注册逻辑 → `harmonia serve` 等命令
- **新增模块**：
  - 适配器层（OpenCode、OpenClaw、Claude Code、Codex）
  - 事件系统
  - HTTP API 层
